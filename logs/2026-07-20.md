### 대화 흐름

#### 1. 부트스트래핑 시도 → 문서 부재로 중단
- **내가 한 말**: `/bootstrap` 명령 실행

- **결과**: 부트스트래핑은 중단되었고, "먼저 기획서를 작성하자"는 다음 단계로 넘어갔다.

#### 2. 아이디어 제시 및 기획 시작
- **내가 한 말**: "계정을 연결해서 클로드 코드 사용량을 확인 할 수 있는 윈도우11 위젯을 만들고 싶어. 어떻게 생각해? 일단 제품 기획서를 만들고 시작하자."
- **AI의 반응**: 아이디어에 긍정적으로 평가하면서, 두 가지 핵심 쟁점을 짚었다.
  1. 사용량 조회를 위한 공식 API가 없어, 로컬 데이터 파싱 방식과 OAuth 연동 중 무엇을 택할지 결정 필요
  2. 진짜 Windows 위젯 보드(Win+W) 연동은 구현 비용이 크므로, 트레이 앱 + 항상 위 미니 창 형태가 더 가볍다는 대안 제시
  이어서 `/plan` 절차에 따라 기획서 작성 방향을 사용자에게 확인했다.
- **결과**: 사용자가 다음 네 가지를 결정했다.
  - 문서 범위: 기획서·PRD·작업계획서 전부
  - 데이터 소스: Claude Code의 OAuth 인증을 재사용 (자격증명 파일을 읽기 전용으로 읽어 비공식 사용량 조회 엔드포인트 호출)
  - 위젯 형태: 트레이 상주 + 항상 위 표시되는 플로팅 창 (윈도우 위젯 보드 통합은 이번 범위에서 제외)
  - 규모: 알림, 사용 이력 차트, 설정 화면, 설치 프로그램까지 포함한 풀 버전

#### 3. 기획서·PRD·작업계획서 작성
- **내가 한 말**: (앞선 결정사항에 대한 확인 답변)
- **AI의 반응**: 결정된 방향을 반영하여 세 개 문서를 순차적으로 작성했다. 특히 사용량 조회 방식이 비공식(문서화되지 않은) 엔드포인트에 의존하는 리스크를 인지하고, 본격 개발 전에 이 방식이 실제로 작동하는지부터 검증하는 단계를 작업계획서 맨 앞에 배치했다.
- **결과**: 아래 네 개 문서가 생성되었다.
  - `CLAUDE.md` — 프로젝트 개요와 핵심 결정 사항, 보안 원칙 정리
  - `docs/planning.md` — 기획서 (기능 10개, 기술 방향 초안: Tauri 2)
  - `docs/prd.md` — 제품 요구사항 문서 v1.0 (필수 기능 8개, 데이터 모델, 이번 범위에서 제외한 것, 성공 지표)
  - `docs/tasks.md` — 작업계획서 (M1~M6 마일스톤, 전체 2~3주 규모)

### 주요 결정사항
- **데이터 소스**: 별도 로그인 없이 Claude Code가 이미 저장해 둔 인증 정보를 읽기 전용으로 재사용해 사용량을 조회한다. 이 정보는 로그·설정·문서 어디에도 기록하지 않는다.
- **위젯 형태**: 진짜 Windows 위젯 보드(Win+W) 연동 대신, 트레이 상주 + 항상 위에 떠 있는 작은 창 형태로 가볍게 구현한다.
- **개발 순서**: 사용량 조회 방식이 공식적으로 지원되지 않는 방법이라, 본격 개발 전에 먼저 "이 방식이 실제로 작동하는가"를 검증하는 단계(M1)를 최우선으로 두고, 실패하면 다른 방식(로컬 대화 기록 분석)으로 전환하기로 했다.
- **규모**: 최소 기능이 아닌 알림, 사용 이력 차트, 설정, 설치 프로그램까지 포함하는 풀 버전으로 진행한다.
- 참고: 아이디어 작업용 폴더(00.아이디어_워크플로우)에 자료가 없어, 문서를 프로젝트의 `docs/` 폴더에 직접 저장했다.
